### ⚡ [CodeFusion](https://github.com/SonamNarula/CodeFusion-a-collaborative-real-time-code-editor)

**Real-time collaborative code editor**: Google Docs, but for code.

Two people can type on the same line and neither loses a keystroke. Sync runs on **Yjs CRDTs**, so it works offline and merges on reconnect, with no "last write wins" overwriting.

```mermaid
%%{init: {'theme':'base','themeVariables':{'primaryColor':'#0E1A2E','primaryBorderColor':'#00F5A0','primaryTextColor':'#E6F1FF','lineColor':'#00D9F5','secondaryColor':'#0A1226','tertiaryColor':'#0A1226','actorBkg':'#0E1A2E','actorBorder':'#00F5A0','actorTextColor':'#E6F1FF','signalColor':'#00D9F5','signalTextColor':'#E6F1FF','noteBkgColor':'#0A1226','noteTextColor':'#E6F1FF','fontFamily':'JetBrains Mono, Segoe UI, Helvetica, Arial, sans-serif'}}}%%
flowchart LR
    A1[Browser A<br/>React + Monaco] <-->|WebSocket rooms| S[Node.js + Express<br/>Socket.io server]
    A2[Browser B<br/>React + Monaco] <-->|WebSocket rooms| S
    S --> R[(Room state<br/>users + document)]
    A1 -. merge via Yjs CRDT .- A2
    S --> X[Code execution]
    S --> AI[AI pair-programmer]
```

**Features**

| Feature | What it does |
| --- | --- |
| 🔴 **Real-time sync** | Edits reach everyone in a room within milliseconds; Yjs CRDTs merge concurrent and offline edits cleanly. |
| 🏠 **Rooms** | Create or join a private room with a unique Room ID, with a one-click copy for sharing. |
| 🌐 **Multi-language** | JavaScript, Python, C++, Java, Go, TypeScript and more. |
| ▶️ **Shared code execution** | Run code and see the output inside the room. |
| 🤖 **AI pair-programmer** | An assistant that lives inside the room. |
| ⏪ **Session replay** | Review how a session unfolded. |
| 🎤 **Interview mode** | A mode built for live coding interviews. |
| ⌨️ **Typing indicators** | See who is typing, live. |
| 🌙 **Dark / light mode** | Theme preference is remembered. |
| 📱 **Responsive UI** | Works across desktop, tablet and mobile. |

<details>
<summary><b>Architecture</b></summary>

<br />

```
CodeFusion/
├── client/                 # React frontend
│   └── src/
│       ├── components/     # Editor (Monaco wrapper, language selector, output panel),
│       │                   # Room (lobby, header, participant list), UI (theme toggle, toasts)
│       ├── hooks/          # useSocket, useEditor, useRoom
│       ├── context/        # Socket and theme providers
│       └── pages/          # Home (lobby) and EditorPage (workspace)
└── server/                 # Node.js + Express backend
    └── src/
        ├── socket/         # roomHandler (create/join/leave), codeHandler (sync, typing)
        └── utils/          # roomManager: in-memory room and user state
```

- **Frontend:** React 18 with a hooks-based structure, Monaco Editor (the VS Code engine), Tailwind CSS with custom dark and light themes, React Router v6 between lobby and editor.
- **Backend:** Node.js and Express for HTTP, Socket.io for WebSocket management, room namespacing and event broadcasting, plus a lightweight in-memory room store.
- **Conflict handling:** Yjs CRDTs, so merging is a property of the data structure instead of custom reconciliation code.

</details>

<details>
<summary><b>Real-time event flow</b></summary>

<br />

| Event | Direction | Purpose |
| --- | --- | --- |
| `room:create` / `room:join` / `room:leave` | Client to server | Room lifecycle |
| `code:change` | Client to server | Broadcast an edit to the room |
| `code:sync` | Server to client | Send current code to someone who just joined |
| `typing:start` / `typing:stop` | Client to server | Typing indicators |
| `user:joined` / `user:left` | Server to client | Keep the participant list accurate |

</details>

<details>
<summary><b>Run it locally</b></summary>

<br />

```bash
git clone https://github.com/SonamNarula/CodeFusion-a-collaborative-real-time-code-editor.git
cd CodeFusion-a-collaborative-real-time-code-editor

# terminal 1: server
cd server && npm install && npm run dev

# terminal 2: client
cd client && npm install && npm run dev
```

Needs Node.js 18+. Copy `.env.example` and set the server port, the client URL (for CORS) and the client's server URL. The frontend is built for Vercel, the backend for Railway or Render, and a Docker setup is included. After deploying, update the CORS origin on the server to match the live frontend URL.

</details>

**Why it was interesting:** collaborative editing is a conflict problem, not just a networking problem. Choosing a CRDT up front meant offline edits and reconnects became a property of the data structure instead of a pile of special cases.

### 🔍 [HireLens](https://github.com/SonamNarula/hirelens-nexus)

**Resume-aware AI interview prep**

Upload a PDF resume and a target role, and get a role-specific preparation report. The design rule: **the candidate and the role are the source of truth; the model is the reasoning layer.**

```mermaid
%%{init: {'theme':'base','themeVariables':{'primaryColor':'#0E1A2E','primaryBorderColor':'#00F5A0','primaryTextColor':'#E6F1FF','lineColor':'#00D9F5','secondaryColor':'#0A1226','tertiaryColor':'#0A1226','actorBkg':'#0E1A2E','actorBorder':'#00F5A0','actorTextColor':'#E6F1FF','signalColor':'#00D9F5','signalTextColor':'#E6F1FF','noteBkgColor':'#0A1226','noteTextColor':'#E6F1FF','fontFamily':'JetBrains Mono, Segoe UI, Helvetica, Arial, sans-serif'}}}%%
flowchart LR
    A[React + Vite] -->|HTTP-only JWT cookie| B[Express API]
    B --> C[pdf-parse<br/>resume text]
    C --> D[Gemini<br/>schema-constrained JSON]
    D --> E[Validate + clamp score]
    E --> F[(MongoDB<br/>owner-scoped reports)]
    F --> A
    F --> G[Puppeteer<br/>ATS-style PDF]
```

**What a report contains**

- A bounded 0 to 100 role-match score
- Skill gaps classified low / medium / high
- Technical and behavioral questions, each with the interviewer's intent and a model answer
- A day-wise preparation plan
- An exportable resume PDF rendered through a headless browser

**What ships today**

| Capability | Status |
| --- | :---: |
| Registration, login, logout, protected session | ✅ |
| PDF resume upload (PDF only, 3 MB limit) and text extraction | ✅ |
| Gemini report generation with schema-shaped JSON | ✅ |
| Match score, skill gaps, questions, preparation plan | ✅ |
| Reports saved per user in MongoDB | ✅ |
| Resume PDF export via Puppeteer | ✅ |

<summary><b>Architecture and request lifecycle</b></summary>

<br />

Backend layering: route → middleware → controller → model or service → external system. Controllers own HTTP, services own external integrations (Gemini, Puppeteer), models own persistence shape.

```mermaid
%%{init: {'theme':'base','themeVariables':{'primaryColor':'#0E1A2E','primaryBorderColor':'#00F5A0','primaryTextColor':'#E6F1FF','lineColor':'#00D9F5','secondaryColor':'#0A1226','tertiaryColor':'#0A1226','actorBkg':'#0E1A2E','actorBorder':'#00F5A0','actorTextColor':'#E6F1FF','signalColor':'#00D9F5','signalTextColor':'#E6F1FF','noteBkgColor':'#0A1226','noteTextColor':'#E6F1FF','fontFamily':'JetBrains Mono, Segoe UI, Helvetica, Arial, sans-serif'}}}%%
sequenceDiagram
    participant B as Browser
    participant U as Upload middleware
    participant C as Interview controller
    participant P as pdf-parse
    participant G as Gemini
    participant DB as MongoDB

    B->>U: multipart POST /api/interview
    U->>U: Check PDF type and 3 MB limit
    U->>C: file buffer + text fields
    C->>P: Extract resume text
    C->>G: Resume + role + context + JSON schema
    G-->>C: Structured report
    C->>C: Clamp match score
    C->>DB: Save report with req.user.id
    DB-->>C: Persisted report
    C-->>B: 201 report payload
```

The browser is never trusted to provide a user id. Identity comes from the verified JWT.

</details>

<details>
<summary><b>Authentication and authorization</b></summary>

<br />

- Passwords hashed with **bcrypt** (cost 12), never stored or returned.
- JWT carries a minimal payload (user id and username) in an **HTTP-only cookie**, 24-hour lifetime, `sameSite=lax`, `secure` in production.
- `authUser` middleware verifies the cookie on every protected route.
- **Authorization lives in the query:** reports are loaded with both the report id and `req.user.id`. Another user's report returns `404`, so nothing leaks about whether it exists.

</details>

<summary><b>Data model</b></summary>

<br />

<details>
<summary><b>API surface</b></summary>

<br />

| Method | Route | Purpose |
| --- | --- | --- |
| `POST` | `/api/auth/register` | Create account, set cookie |
| `POST` | `/api/auth/login` | Log in, set cookie |
| `POST` | `/api/auth/logout` | Clear cookie |
| `GET` | `/api/auth/me` | Current user (protected) |
| `POST` | `/api/interview` | Upload resume + job description, generate report |
| `GET` | `/api/interview` | List the current user's reports |
| `GET` | `/api/interview/report/:interviewId` | Fetch one owned report |
| `POST` | `/api/interview/resume/pdf/:interviewReportId` | Generate the resume PDF |

Status codes are deliberate: `400` invalid input, `401` unauthenticated, `404` not found for this user, `409` duplicate account, `502` unusable upstream AI output, `503` provider or configuration unavailable.

</details>

<details>
<summary><b>Security model</b></summary>

<br />

**Implemented:** bcrypt hashing, HTTP-only cookie, JWT verification, protected routes, owner-scoped queries, CORS allowlist, PDF-only uploads, 3 MB limit, generic error responses to the browser, secrets kept out of source control.


</details>

<details>
<summary><b>Engineering decisions worth calling out</b></summary>

<br />

| Decision | Why |
| --- | --- |
| Structured JSON output + backend parsing | The UI needs predictable fields; invalid output is rejected, not rendered. |
| Score clamped server-side | Model output is untrusted input. |
| Explicit failure when the AI provider fails | No success-shaped fake reports. |
| Model name set by environment variable | Model availability and quotas change; deployments shouldn't need a code change. |
| Memory upload storage for the MVP | Simple and fine for small PDFs, with the object-storage path documented for scale. |
| Synchronous request for the MVP | Easy to trace end to end, with a clear queue boundary for later. |

</details>

## 🔧 Engineering notes

Real problems from building HireLens, and how I separated the causes. Debugging by boundary is a habit I take seriously.

| Symptom | Actual cause | Fix |
| --- | --- | --- |
| Login returned a generic 500 | Database was connected, but `JWT_SECRET` wasn't loaded in the running process | Added the variable, restarted, added startup validation so missing config fails early |
| Account creation blocked in the browser | App opened at `127.0.0.1`, CORS allowlist only had `localhost` | Allowlisted both local origins; never a wildcard with credentials |
| AI analysis failing with "Internal server error" | Several stacked causes: missing key, stale processes, duplicate servers on one port, a retired model, a temporary provider `503` | Checked each layer independently, made the model configurable, picked one that answered a direct test request |
| `app.listen is not a function` | Typo: `module.export` instead of `module.exports` | Fixed the CommonJS export |
| PDF parsing broke on the local Node version | Newer parser version was incompatible | Pinned the compatible `pdf-parse` version and tested with a real PDF |
| Vite build failed | Latest Vite needed a Node API unavailable in Node 20.11 | Pinned the compatible Vite major |

**The lesson:** "the key exists in `.env`" is not enough. The running process must load it, the model must be available to that key, and the request must return something usable. Configuration, process lifecycle and provider availability are separate problems.

## 🧭 How I build

1. **Deterministic where it matters, AI where it helps.** AcornFolio keeps the maths in code; HireLens validates and clamps model output.
2. **Fail loudly.** An explicit error beats a plausible-looking wrong answer.
3. **Authorize at the query, not just the route.** A valid session isn't permission to read everything.
4. **Keep secrets server-side.** Browsers are untrusted.
5. **Document what is real.** READMEs should list what works today and mark what's planned.
6. **Debug by boundary.** Process, environment, network, auth, provider, database, UI: check each layer on its own before guessing.
7. **Design the migration path.** An MVP can be simple if its next step is clear.
